# TDK notes repository

The top-level repository of one student's TDK semester. It holds the notes, the consultation
summaries and the slides, and it includes the paper and the code as Git submodules, so that one
clone holds everything and an AI agent working here sees all three.

```
notes/
  anchors/            the three anchors: manifest.md, spine.md, full-draft.md
  consultations/      one file per consultation, YYYY-MM-DD.md, written by you after each one
slides/               presentations, one folder per talk; the TDK talk in slides/tdk/
paper/                submodule: the Overleaf-synced paper repository
code/                 submodule: the code repository, what Zenodo archives
lifecycle.md          regenerated by CI: where you are in the lifecycle
burndown.csv, burndown.svg   regenerated by CI: the paper's counts over time
```

## Setting up

1. Create this repository from the template, private, named after your topic.
2. Add the paper and the code as submodules, then commit:

   ```sh
   git submodule add <paper repository url> paper
   git submodule add <code repository url> code
   git commit -m "Add the paper and the code"
   ```

3. Add both advisors with write access. Clone with `git clone --recurse-submodules`.
4. After each consultation, write `notes/consultations/YYYY-MM-DD.md` and move the submodule
   pointers, so the state you discussed is the state we can check out.

## What CI checks

`.github/workflows/lifecycle.yml` runs on every push and on Monday mornings. It regenerates
`lifecycle.md`, one row per lifecycle step that can be checked from files, present or missing,
keyed to the phase set in `paper/thesis.tex` (`\lintphase`). An anchor counts when its file is
longer than a stub. The paper's burn-down counts are appended to `burndown.csv` and drawn into
`burndown.svg`, both committed by the workflow. Judgement stays with the consultation; this is
the inventory.

## The agent skills

The skills live in the paper repository, so the paper's commit fixes the skills that review it.
`.claude/skills/self-score` and `.claude/skills/reviewer-passes` here are links into
`paper/.claude/skills/`; they resolve once the paper is a submodule.

`self-score` scores the reviewer PDF on the review sheet's criteria, in the sheet's words, and
names the cheapest fix. `reviewer-passes` reads the paper as its reviewers will: the skim reviewer
on the skim view, and a panel of disjoint expert personas on the reviewer PDF. Both read the
evidence paper CI builds for one commit, fetched with `paper/scripts/review/review.py`, and give
each persona only its own inputs. Name the spine when you run them from here:
`notes/anchors/spine.md`. They answer in chat and write nothing, unless a run is recorded as one
issue on the paper repository; the paper guide's lifecycle chapter says when.
